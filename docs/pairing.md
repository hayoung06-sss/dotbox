# 모듈 역할과 연결 명세 (초안 v0.1)

> 상태: **제안**. 아직 구현하지 않았다. 구현하면서 바뀌는 내용은 이 문서를 먼저 고친다.

DotBox는 같은 구성의 모듈 2개(왼쪽/오른쪽)로 이뤄진다. 이 문서는 두 모듈이 어떻게 자기 역할을 알고,
상대를 찾고, 서로 같은 펌웨어인지 확인하는지 정한다.

## 1. 결정 사항

- **두 모듈은 같은 펌웨어 이미지를 쓴다.** 왼쪽/오른쪽용으로 따로 빌드하지 않는다.
- **역할은 런타임에 정한다.** 이미지 밖의 플래시 영역에 역할을 저장하고 부팅할 때 읽는다(2장).
- **두 모듈의 펌웨어가 같은지 확인한 뒤에만 게임을 시작한다.** 엔진 버전만 맞는 것으로는 부족하다.
  두 모듈은 게임 상태 메시지를 주고받으므로 게임 코드까지 같아야 한다(3장).

## 2. 역할 결정

역할 값은 `dotbox_core::display::Side`(`Left` = 마스터, `Right` = 슬레이브)를 그대로 쓴다.

### 2.1 저장 위치

- 펌웨어 파티션 테이블에 전용 데이터 파티션 `dotbox`(4 KiB)를 둔다. 앱 파티션과 분리되어 있어서 펌웨어를 다시 구워도 지워지지 않는다.
- 레코드 형식(리틀 엔디언):

| 오프셋 | 크기 | 내용 |
|---|---|---|
| 0 | 4 | 매직 `b"DBXR"` |
| 4 | 1 | 레코드 형식 버전 = 1 |
| 5 | 1 | 역할: 0 = Left, 1 = Right |
| 6 | 6 | 상대 모듈 MAC(모르면 모두 0) |
| 12 | 4 | 앞 12바이트의 CRC32 |

### 2.2 역할을 정하는 방법

1. **`dotbox flash --side <left|right>`** (기본 경로): 앱을 구운 뒤 해당 역할 레코드를 `dotbox` 파티션에 쓴다.
   이때 상대 MAC은 0으로 초기화되므로 다시 짝을 맺는다.
2. **기기에서 직접 선택** (예비 경로): 부팅했을 때 레코드가 없거나 CRC가 틀리면 역할 선택 화면을 띄운다.
   조이스틱을 왼쪽/오른쪽으로 기울여 고르고 버튼으로 확정하면 레코드를 저장한다.
   CLI 없이 기기를 초기화했을 때를 위한 경로다.
3. **강제 재선택**: 부팅할 때 조이스틱 버튼을 3초 누르고 있으면 2번 화면으로 들어간다.

### 2.3 플랫폼 구분

- 레코드를 읽고 쓰는 일은 `Storage`처럼 트레잇으로 추상화한다. `dotbox-esp`는 파티션을, `dotbox-sim`은 실행 인자나 고정값을 쓴다.
- 시뮬레이터는 한 프로세스에서 두 역할을 모두 흉내 내므로 핸드셰이크를 가짜 `Link`로 통과시킨다.

## 3. 펌웨어 일치 확인

### 3.1 빌드 식별자

| 필드 | 크기 | 내용 | 출처 |
|---|---|---|---|
| `protocol_version` | 2 | 모듈 간 메시지 형식 버전. 형식이 바뀌면 올린다 | `dotbox-core` 상수 |
| `engine_version` | 3 | 엔진 major.minor.patch | `dotbox-core`의 `CARGO_PKG_VERSION` |
| `game_id` | 4 | 게임 이름 해시(FNV-1a 32) | 게임 crate 이름 |
| `build_id` | 8 | 펌웨어 이미지 ELF SHA-256 앞 8바이트 | ESP-IDF 앱 설명자(`esp_app_get_description`) |

- **일치 판정은 `build_id`로 한다.** 같은 이미지이면 나머지 필드도 반드시 같다.
- 나머지 필드는 불일치 **원인**을 알려 주는 데 쓴다. 예: "엔진 버전 다름 0.1.0 / 0.2.0", "게임 다름".

### 3.2 핸드셰이크

ESP-NOW로 한다. 메시지 앞에는 공통 헤더(매직 2바이트 + 메시지 종류 1바이트)를 붙인다.

```
오른쪽(슬레이브)                         왼쪽(마스터)
  │  Hello{role, 빌드 식별자} ──────────▶  │  (상대 MAC 모르면 브로드캐스트, 200ms마다 반복)
  │                                       │  역할 확인 → 빌드 식별자 비교
  │  ◀────────── Accept{build_id}          │  일치
  │  ◀────────── Reject{reason, 내 식별자}  │  불일치
```

- `Hello`는 연결 전인 **오른쪽(슬레이브)** 만 보내고, 판정은 **왼쪽(마스터)** 이 한다. 마스터가 재부팅하면 슬레이브가
  끊김을 감지해 다시 `Hello`를 보내므로 연결이 복구된다. 메시지 형식은 [game-api.md](game-api.md) 7장.
- `Hello`에는 빌드 식별자와 함께 그 모듈의 하드웨어 구성(부저, 홀센서, 확장 장치 목록)을 담는다(하드웨어 구성은 나중 단계).
  같은 이미지라도 모듈마다 하드웨어가 다를 수 있기 때문이다([modes.md](modes.md) 6.1). 구성 차이는 거부 사유가 아니다.
- `Accept`를 받거나 보내면 상대 MAC을 역할 레코드에 저장하고, 그다음부터는 그 MAC으로만 유니캐스트한다.
- `Reject` 사유는 `RoleConflict`(둘 다 같은 역할), `ProtocolMismatch`, `BuildMismatch` 세 가지다.
  `BuildMismatch`일 때는 3.1의 다른 필드를 비교해 원인을 자세히 알려 준다.
- 상대 MAC을 저장해 둔 상태에서 다른 DotBox가 `Hello`를 보내면 무시한다(주변의 다른 조 기기와 섞이지 않게 하려는 것).

### 3.3 불일치 시 동작

- 게임을 시작하지 않는다. 엔진은 씬을 시작하지 않고 대기한다. 매트릭스에는 아무것도 띄우지 않는다.
- 상태 LED가 불일치 패턴으로 깜박인다(4장).
- 시리얼 로그에 양쪽 빌드 식별자와 거부 사유를 모두 출력한다. 자세한 원인은 `dotbox monitor`로 확인한다.
- 슬레이브가 재부팅해 새 `Hello`를 보내면 다시 판정한다. 그래서 펌웨어를 다시 구우면 전원을 껐다 켜지 않아도 복구된다.

불일치는 펌웨어를 다시 구우면 고칠 수 있는 **설정 문제**라서 상태를 표시한다.
기기에서 생긴 런타임 오류는 표시하지 않고 재시작한다([errors.md](errors.md)).

## 4. 연결 상태 표시

### 4.1 상태

| 상태 | 뜻 |
|---|---|
| `Searching` | 상대를 찾는 중(`Hello`를 보내고 응답이 없음). 연결이 끊긴 뒤에도 이 상태로 돌아간다 |
| `Connected` | 핸드셰이크 성공. 게임 실행 가능 |
| `Rejected(reason)` | 핸드셰이크 거부(3.2의 사유) |

역할을 정하지 못한 동안(역할 선택 화면)은 연결을 시도하지 않으므로 상태를 표시하지 않는다.

### 4.2 기기: 상태 LED

모듈마다 매트릭스와 별도로 단색 LED 하나를 둔다(핀은 루트 CLAUDE.md 하드웨어 표). 각 모듈은 자기가 아는 상태를 표시한다.

| 상태 | LED 패턴 |
|---|---|
| 역할 미정 | 꺼짐 |
| `Searching` | 느린 깜박임(1 Hz, 켜짐 비율 50%) |
| `Connected` | 계속 켜짐 |
| `Rejected` | 빠른 깜박임(4 Hz). 사유는 시리얼 로그로 본다 |

### 4.3 시뮬레이터와 GUI

- 시뮬레이터는 상태가 바뀔 때 터미널에 로그를 남기고, 창에도 상태 표시를 그린다.
- 테스트할 때는 가짜 `Link`로 끊김·거부를 일으켜 각 상태를 재현할 수 있게 한다.

### 4.4 엔진 쪽 구성 (제안)

- 연결 상태는 핸드셰이크 상태 기계가 `dotbox-core`에서 계산한다.
- 표시는 hal 트레잇으로 추상화한다(가칭 `StatusIndicator::show(LinkState)`). 플랫폼은 상태만 받고 표시 방법은 각자 정한다.
- LED 깜박임 패턴(상태와 현재 시각으로 켜짐/꺼짐 계산)은 `dotbox-core`의 순수 함수로 두고 `dotbox-esp`가 매 틱 호출한다. PC에서 테스트할 수 있다.

### 3.4 엔진 쪽 구성 (제안)

- 핸드셰이크 상태 기계와 메시지 인코딩·디코딩은 `dotbox-core`에 둔다. 하드웨어와 무관하므로 PC에서 가짜 `Link`와 가짜 `Clock`으로 테스트한다.
- 빌드 식별자는 플랫폼이 넘겨준다. `dotbox-esp`는 앱 설명자에서 읽고, `dotbox-sim`은 고정값을 쓴다.
- 메시지는 고정 크기 버퍼에 인코딩한다. 힙 할당을 하지 않는다.

## 5. CLI 쪽 보조

기기 간 확인은 3장이 맡는다. CLI는 불일치가 **생기지 않게** 돕는다(자세한 내용은 [cli.md](cli.md)).

- `dotbox flash --side both`: 한 번만 빌드하고 같은 이미지를 두 모듈에 차례로 굽는다. 권장하는 기본 사용법이다.
- 모듈 하나만 구울 때는 그 모듈에 구운 `build_id`를 `.dotbox/local.toml`에 기록한다.
  두 모듈의 기록이 다르면 "다른 모듈도 다시 구워야 합니다"라고 경고한다.

## 미결 사항

- 역할 선택 화면의 구체적인 그림(글꼴이 생긴 뒤 정한다).
- 상태 LED 핀과 색. 하드웨어 담당과 확정한다.
- 기기 쪽 `build_id` 출처. espflash로 구운 이미지의 앱 설명자에 ELF SHA-256이 채워지는지 실기기에서 확인한다.
  채워지지 않으면 빌드할 때 식별자를 생성해 펌웨어에 넣는다. CLI(`dotbox flash`)는 ELF 파일의 SHA-256으로 기록한다.
- 연결된 뒤 끊겼을 때 게임 동작(재연결 대기 시간, 일시정지). 엔진 명세 5단계(통신 어댑터와 세션)에서 정한다.
  상대 모듈이 재시작한 경우도 여기에 해당한다.
- 결합 감지 홀센서(GPIO26)를 역할 판정이나 연결 확인에 쓸지.
